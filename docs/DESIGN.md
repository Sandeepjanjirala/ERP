# EduNexa: design

**EduNexa is a school ERP for school groups with many branches, built with Django.**

Status: Phases 1 to 3 complete (5 and 6 November 2026); Phases 4 to 6 are planned

This document describes where the project is going: the product, its modules, how the code is organised, how the main workflows run, and the order we build it in. Phases 1 to 3 are built; the rest is planned. We build it phase by phase (see [Roadmap](#14-roadmap)).

---

## 1. Goals

EduNexa should show a reviewer, within two minutes, that its author can build production-quality Django:

1. **A live demo** they can open from your resume, with one-click logins for each role (admin, principal, teacher, accountant, parent, student).
2. **A README** with screenshots, an architecture diagram, the tech stack, and a quick start that works.
3. **Clean, modular code**: domain apps, a services/selectors layer, tests, and green CI.
4. **A documented REST API** with Swagger at `/api/docs/`.
5. **Real-world depth**: concurrency control, approval workflows, online payments, background jobs, and an audit trail.

## 2. The one-name rule

**EduNexa is the product name, and it never changes.** The school using EduNexa is a separate thing: it is data, not branding. Gmail works the same way: the product is always "Gmail", even when your company's name appears inside it.

| Place | What it shows |
|---|---|
| Browser tab | `Attendance · EduNexa` (always the page name, then EduNexa) |
| Sidebar, login page | EduNexa logo and "School ERP" |
| Emails | Sender "EduNexa", EduNexa footer |
| Report card and fee receipt PDFs | The school's name and branch in the header (it is their document); "Generated by EduNexa" in the footer |
| Workspace label in the sidebar | The school and branch you are working in, for example `Greenfield · Madhapur` |
| API docs | "EduNexa API" |
| GitHub | Rename the repo `ERP` → `edunexa` |

How it is built: one `BRAND` setting (`name`, `tagline`), read by a context processor. No template types the name by hand. The word "Demo" is never part of any name. The demo data uses a fictional school group, *Greenfield Group of Schools*, which can be renamed in one line of the seed command.

## 3. Starting point: keep, fix, add

**Keep.** The current code has a strong core, and these are interview talking points:
- Database constraints for business rules: one register per class per day, marks never above the maximum, valid role/branch combinations.
- Row locks plus version numbers, so two people saving the same register or mark sheet can't overwrite each other.
- The result workflow Draft → Submitted → Published, with principal approval and reopening with a reason.
- An audit log that records before/after values.
- Branch-scoped permissions, login throttling, forced password change, and strict security headers (CSP).
- 59 tests, including concurrency tests on PostgreSQL.

**Fix.** These are things a reviewer notices quickly:
- Everything lives in one `school` app, including a 400-line `views.py`. It gets split into domain apps.
- Templates and CSS are squashed onto single lines, which is unreadable in code review.
- `from .models import *`, and role names typed as raw strings (`'teacher'`) everywhere. These become constants.
- The README mentions ChatGPT and an "earlier marketing demo", and the first commit adds the whole project at once. Together they read as a code dump.
- The product name comes from demo data ("Vidya Schools · Demo").

**Add.** A REST API, background jobs, a parent portal, fees and payments, timetable, notifications, PDFs, charts, and a live demo.

## 4. Users and roles

| Role | Scope | Main job in EduNexa |
|---|---|---|
| Super admin | Whole school group | Branches, academic years, all staff, group-wide reports |
| Branch admin | One branch | Classes, subjects, teachers, students, fee plans |
| Principal | One branch | Approves results, watches attendance and performance, announcements |
| Teacher | Assigned classes/subjects | Attendance (class teacher), marks, leave approvals for their class |
| **Accountant** (new) | One branch | Invoices, collecting payments, receipts, dues follow-up |
| **Parent** (new) | Own children | Attendance, results, report cards, paying fees, applying for leave |
| Student | Self | Timetable, attendance, results, report cards, announcements |

Roles stay a fixed list. Each permission is checked in three layers: the menu only shows what is allowed, every query is filtered to the user's scope, and every write checks again. A forged URL for someone else's record returns 404. A forbidden action returns 403.

## 7. Architecture

```
          Browser (HTML + HTMX)                    Mobile app / Postman / other systems
                   │  session cookie                            │  JWT token
                   ▼                                            ▼
  ┌───────────────────────────── Django (Gunicorn) ──────────────────────────────┐
  │   Web views + templates (HTMX partials)          REST API /api/v1 (DRF)      │
  │                   └──────────────────┬────────────────────┘                  │
  │      policies.py    who may do what (role + branch + object checks)          │
  │      selectors.py   every read, already filtered to the user's scope         │
  │      services.py    every write: transaction, row lock, version check, audit │
  │      models.py      tables, database constraints, validation                 │
  └──────────────┬──────────────────────────┬──────────────────────┬─────────────┘
                 ▼                          ▼                      ▼
            PostgreSQL                 Redis (cache,         Celery worker + beat
       (SQLite for quick runs)         task queue)      emails, PDFs, reminders, demo reset
```

Rules the code follows:

1. **Thin views.** A web view and an API view do the same three things: read the input, call a selector or service, then render HTML or JSON. Business logic exists once, so the web and the API can never disagree about permissions.
2. **Reads go through selectors.** `students_for(user)` already excludes other branches, so a teacher's query can't even see another branch's students.
3. **Writes go through services.** A service re-checks the policy, locks rows, checks the version number, writes an audit event, and queues follow-up jobs with `transaction.on_commit`. Emails are sent only if the save really happened.
4. **Slow or external work runs in Celery**: email, PDFs, payment checks and reminders, never inside a request.
5. **Apps depend downwards only, never in a circle:**

```
 Layer 4   reports · demo                            reports read everything; demo creates sample data
 Layer 3   attendance · exams · fees · communication
 Layer 2   academics · students
 Layer 1   organization · accounts · audit
 Layer 0   core                                      base models, branding, middleware, utilities
```

## 9. Data model changes

Existing tables move into their new apps unchanged in meaning. The new and changed tables are:

| App | Table | Change | Rule the database enforces |
|---|---|---|---|
| organization | Organization, Branch | + address, phone, email, logo; branch receipt prefix | Branch code is unique |
| accounts | User | + `accountant` and `parent` roles, phone | Role and branch must match (exists) |
| academics | Grade | New: Class 1 … Class 12, with an order | Promotion moves students to the next grade |
| academics | Term | New: Term 1 and Term 2 inside a year | Term dates fall inside the year |
| academics | Period, TimetableSlot | New | A class, or a teacher, can't be booked twice in the same period |
| students | Guardian, StudentGuardian | New: parents linked to one or more children | Exactly one primary guardian per student |
| attendance | LeaveRequest | New | End date on or after the start date |
| exams | Exam | + term | Exists |
| exams | GradeBand | New: A1 = 91–100 … E | Bands may not overlap |
| fees | FeeHead, FeePlan, FeePlanItem | New | One plan per branch + year + grade |
| fees | Invoice, InvoiceLine | New | Amount paid never exceeds the total |
| fees | Payment | New | Gateway payment ID is unique, so a repeated webhook can't pay twice |
| fees | Receipt, ReceiptCounter | New | Receipt numbers are unique and gapless per branch and year |
| communication | Announcement, Notification | New | None |
| audit | AuditEvent | + request ID, indexes | Append-only |

There is no real data yet, so Phase 1 starts a fresh migration history. The local `db.sqlite3` is recreated and the demo data is seeded again.

## 10. Key workflows

**Exam results.** This exists and stays.

```
                 submit (teacher)               publish (principal)
      Draft ─────────────────────▶ Submitted ─────────────────────▶ Published
        ▲                              │                                │
        └───────── reopen with a reason (principal) ◀───────────────────┘
```
Marks can only be edited in Draft. When results are published, a background job notifies students and guardians, and the report card PDF becomes available.

**Daily attendance**
1. The teacher opens **My day** and sees today's classes from the timetable and their class-teacher class.
2. One tap per student (P / A / L / E), or "all present". HTMX saves without reloading the page.
3. The service locks the classroom, checks the version, writes the register and records an audit event.
4. After the save commits, Celery emails or notifies the parents of absent students.
5. Approved leave pre-fills "Excused". A stale browser tab gets "Someone else changed this register. Reload" (HTTP 409 in the API).

**Fees and online payment**

```
   Issued ──part payment──▶ Partly paid ──balance paid──▶ Paid
     │ └───────────────────── full payment ─────────────────▲
     └──▶ Cancelled (admin, with a reason, only if nothing was paid)
```
"Overdue" is computed (due date passed and balance above zero) rather than stored, so it can never be out of date.

```
  Parent              EduNexa                                   Razorpay (test mode)
    │ Pay ₹12,500       │                                                │
    ├──────────────────▶│ create order for the invoice balance ─────────▶│
    │◀── checkout ──────┤                                                │
    ├──────────────────── pays inside Razorpay checkout ────────────────▶│
    │                   │◀────────── webhook: payment captured ──────────┤
    │                   │ 1. verify the webhook signature                │
    │                   │ 2. payment ID already recorded? stop here (safe to repeat)
    │                   │ 3. lock invoice → record payment → next receipt number
    │                   │ 4. after commit: email the receipt PDF (Celery)
    │◀── receipt ───────┤                                                │
```
Cash and UPI paid at the school counter go through the same service, so receipts and audit work the same way. Payment providers sit behind a `PaymentGateway` interface. A built-in **Sandbox** gateway works with no keys, so tests and the live demo never depend on Razorpay.

**Leave requests.** The parent applies with dates and a reason. The class teacher approves or rejects it. Approved days show as "Excused", and the parent is notified.

**Year-end promotion.** The principal picks a class and next year's classroom. A preview lists who moves up and who stays. On confirmation, the new enrollments are created and the old ones closed in one transaction.

**Live demo.** When `DEMO_MODE` is on, the login page shows "Try it as: Admin · Principal · Teacher · Accountant · Parent · Student". A nightly Celery job resets the demo data.

- Design tokens (colours, spacing, radius, type), with light and dark themes.
- Reusable components: stat card, data table with sorting, filters and pagination, status badge, modal, toast, empty state, form field.

## 12. REST API

- Base URL `/api/v1/`. Swagger UI at `/api/docs/`, ReDoc at `/api/redoc/`. The docs are generated by drf-spectacular and self-hosted, so the CSP stays strict.
- Login: JWT (short-lived access token, rotating refresh token) for apps; session login for the browsable API.
- It uses the **same selectors, services and policies** as the web pages.
- Conventions: pagination, filtering (`?classroom=&status=`), ordering, one error format, **409 Conflict** for a stale `version`, 404 for out-of-scope records, rate limits (stricter on login).

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/auth/token/` · `POST /api/v1/auth/token/refresh/` | Log in, refresh |
| `GET /api/v1/me/` | Current user, role, branch, children (for parents) |
| `GET /api/v1/students/?search=&classroom=` | Students in your scope |
| `GET / PUT /api/v1/classrooms/{id}/register/?date=` | Read / save a daily register (with `version`) |
| `GET /api/v1/exams/?status=` · `PUT /api/v1/exams/{id}/marks/` | Exams, mark sheets |
| `POST /api/v1/exams/{id}/submit/` · `/publish/` · `/reopen/` | Result workflow |
| `GET /api/v1/invoices/` · `POST /api/v1/invoices/{id}/pay/` | Fees, start an online payment |
| `POST /api/v1/payments/webhook/` | Payment provider callback (signature checked) |
| `GET /api/v1/announcements/` · `GET /api/v1/notifications/` | Communication |

Phase 2 built the API for every existing feature; the full list is in [API.md](API.md). The fees endpoints arrive with Phase 4 and the communication endpoints with Phase 3, alongside those features. Password reset by email stays a web flow.

## 13. Tech stack

| Area | Choice | Why |
|---|---|---|
| Framework | Python 3.12, Django 5.2 LTS | Long-term support until April 2028 |
| API | Django REST Framework, SimpleJWT, drf-spectacular, django-filter | The standard Django API stack that job posts ask for |
| Database | PostgreSQL 17 (SQLite for quick local runs) | Row locks and constraints, as in production |
| Background jobs | Celery + Redis, scheduled jobs with Celery beat | Emails, PDFs, reminders, nightly demo reset |
| Cache | Redis | Dashboard numbers |
| Frontend | Django templates, HTMX, Chart.js, plain CSS with tokens | Interactive without a separate frontend app |
| PDFs | ReportLab | Installs with pip on Windows and Linux; no system libraries |
| Payments | Razorpay test mode + built-in Sandbox gateway | Real integration, no real money |
| Email | Terminal output (quick run), Mailpit (Docker, view emails at `localhost:8025`), SMTP (production) | |
| Code quality | ruff (lint + format), pre-commit, pytest + pytest-django + factory_boy, coverage | |
| CI | GitHub Actions: lint → tests on PostgreSQL + Redis → coverage → Docker build | Green badge in the README |
| Running in production | Docker, Gunicorn, WhiteNoise, JSON logs with request IDs, optional Sentry, `/health/` endpoint | |

**Running on your PC, two ways:**
1. **Quick (no Docker):** `run_server.bat`. SQLite; background jobs run immediately inside the request; emails print in the terminal. Celery doesn't officially support Windows, so this mode doesn't need it.
2. **Full (Docker Desktop):** `docker compose up`. PostgreSQL, Redis, Celery worker and beat, and Mailpit: the same setup as production.

## 15. Out of scope for now

SMS/WhatsApp (paid gateways), transport tracking, library, hostel, payroll/HR, native mobile apps, AI features, and multi-school SaaS. Every record already hangs off Organization → Branch, so multi-school support can be added later without redesigning.
